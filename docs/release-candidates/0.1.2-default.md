# SmolBox 0.1.2 default runtime validation

Status: **accepted for the scoped 1.14.6 default candidate**, September 10, 2026
(final UTC timestamps fall on September 11). No tag, publication, push or pull
request was created. See the [JSON evidence](0.1.2-default.json).

## Default and upgrade behavior

SmolBox now expects **SmolVM 1.14.6** when a managed worker's `runtime_version`
is omitted. Host examples and CI manifest handling use the same default on
Linux x86_64 and macOS Apple Silicon. Exact version checks remain mandatory.

Applications keeping a 1.14.1 worker must explicitly configure
`runtime_version: "1.14.1"` before upgrading SmolBox, or upgrade their worker
using the [drain and upgrade procedure](../host-integration.md#upgrading-a-worker).
The Elixir dependency does not install SmolVM. A mismatch prevents new execution;
there is no automatic fallback or version inference from an arbitrary server.
The documented host `resize2fs` prerequisite for smaller 1.14.6 disks still applies.

The [earlier native macOS and Linux report](0.1.2-macos.md) describes the preceding
candidate, which kept the old default. Its observations remain historical and
are not rewritten as tests of this change.

## Preserved failure and correction

The first Linux run passed thirteen of fourteen cases. The test with delayed execution
failed waiting for its intended interruption point. Inspection found
that the test proxy still used a fixed 15-second receive budget, despite the
constrained worker's configured 55-second receive budget. The proxy's client
also used its shorter defaults, and the setup wait was fixed at 30 seconds.

The test proxy now honors its configured endpoint's receive budget, its client
inherits the worker's operation/receive budgets, and setup uses the existing
Linux observation allowance. The execution, cancellation, uncertainty and
cleanup assertions are unchanged, as are production stage deadlines and host
controls. The complete Linux runtime rerun passed. Both platforms' final quality,
language, runtime and durable checks used the corrected candidate. The initial
failed result and log remain in the JSON evidence.

## Cleanup and scope

Both final stores had zero pending records and reserved slots. Task workers,
their VMs and the private Mac database were stopped. Existing host workers and
databases were preserved. The Linux recovery controller recreated a clean
outer disk from the unchanged baseline, and its management port closed.

This validates the default and its documented compatibility path. It does not
repeat the earlier artifact-building, exhaustion or separate API-service-fault
campaigns; those remain evidence for their recorded configurations. Mac execution
covered ordinary compatibility and lifecycle recovery. The five additional
boundary cases ran only in Linux. No hard macOS host limits or general hostile-code
security certification is claimed; qualification remains `:development`.

All CI commands were executed locally on the two hosts. No GitHub Actions run,
release or public deployment is implied by this report.
