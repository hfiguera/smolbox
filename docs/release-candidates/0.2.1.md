# SmolBox 0.2.1 release preparation

Status: prepared and validated locally, September 26, 2026 UTC.
**Not committed, published or tagged.**

Base: `309e2b6cf2ba379b302173df819427dbc7604393` (merged smolvm 1.19.0 qualification).
Branch: `release/0.2.1`.

## Scope and compatibility

This release delivers qualified smolvm 1.19.0 support and the explicit managed
store contract, together with internal separation, example/documentation work
and test reliability improvements since 0.2.0. The worker default becomes
1.19.0; supported explicit pins remain available.

The [upgrade guide](../upgrading-to-0.2.1.md) documents worker and checkpoint
pinning, the 0.x patch policy, the absence of new SmolBox store migrations from
0.2.0, and the separate worker upgrade/rollback limits. It links the earlier
0.2.0 migration requirements for applications upgrading from 0.1.x.

The community workspace remains locked to the published 0.2.0 dependency and
explicit smolvm 1.17.0. Historical articles and qualification records retain
the versions they actually exercised. No new runtime feature is introduced by
this preparation.

## Evidence and publication boundary

[Main CI](https://github.com/hfiguera/smolbox/actions/runs/36249413273) passed at

executable code to that base after removing documentation and source positions;

This preparation reuses those recorded real-worker results. It does not label
them as fresh live runs of a future release commit. Local preparation checks and
exact archive receipts are recorded below; required CI on the final release
commit is a separate publication gate.

## Publication handoff

1. Review and commit/merge the preparation. Verify required CI on the exact
   release commit and compare every packaged file with the validated archive
   manifest. Review executable-source equivalence to the qualification; changes
   to runtime behavior, dependencies or fixtures require the applicable live
   checks again. Follow the CI guide's exact-candidate qualification requirements
   before publication, recording any final live runs against that commit.
2. Complete the authenticated publishing dry run in the publishing environment.
   This preparation does not read or modify credentials, or establish that the
   publisher's authentication is still valid.
3. Tag the reviewed release commit as `v0.2.1`, publish the package and documentation,
   and create the GitHub release using the [prepared notes](0.2.1-release-notes.md).
4. Verify the published checksum/contents, a clean registry installation and hosted
   versioned documentation. The draft release links become live only after this
   publication; local link validation does not verify future remote pages.

No tag, publication, push or GitHub release is performed by this preparation.
