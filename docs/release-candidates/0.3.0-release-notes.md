# SmolBox 0.3.0

SmolBox 0.3.0 lets Elixir applications provision from approved registry sources,
export prepared disk state, capture and restore checkpoints, and create live
branches. Each path has durable identity, explicit recovery and its own retention
and capacity accounting.

## What is new

- **Images and registry artifacts:** immutable source specifications, exact worker
  approvals, host-owned credential resolution, typed machine image inventories
  and managed OCI pulls.
- **Exports:** publish a stopped machine to an approved registry destination and
  reuse its disk state for a new boot. Publication claims survive source deletion.
- **Checkpoints:** capture an idle, offline bare guest and restore an independent
  machine with its disk and RAM. Captured artifacts have explicit retention and
  release, separate from machine deletion.
- **Branches:** create a child from an idle, offline bare source on the same worker.
  Durable lineage and conservative backing allowances keep cleanup explicit.
- **Measurements:** a reproducible physical Linux comparison covers fresh
  provisioning, exports, checkpoints, branches and retained machine reuse. It
  includes verified results, preparation costs, raw trials and cleanup accounting.
- Improve CI fixture readiness and recovery/store test synchronization. Add a
  practical article about terminal disconnects and uncertain command outcomes.

Read the [provisioning comparison](https://hexdocs.pm/smolbox/0.3.0/provisioning-performance.html)
for the measured workload and limits. The numbers are not a universal ranking.

## Upgrade note

**Upgrade shared controllers, readers and store adapters together before enabling
the new features.** New records selectively use codec v10–v13 and additional store
capabilities. The PostgreSQL example needs no additional SQL migration from 0.2.x,
but older readers cannot decode the new records, including retained history after
machine deletion. Custom adapters must implement the new atomic operations and
resource projections before advertising support.

The default worker remains **smolvm 1.19.0**, unchanged from 0.2.1. Worker
installation is separate. Pin existing workers and checkpoint approvals to their
actual versions; upgrading from 0.2.0 does not upgrade a 1.17.0 worker for you.

Read [Upgrading to 0.3.0](https://hexdocs.pm/smolbox/0.3.0/upgrading-to-0.3.0.html)
for the sequence, capabilities, retention and rollback limits. Applications coming
from 0.1.x must also follow the 0.2.0 migration procedure.

## Evidence and limits

Registry provisioning has Linux and macOS evidence. Managed captures and branches
have Linux acceptance evidence; that does not establish macOS live qualification.
The physical Linux benchmark covers one workload on one host with warm caches.
See [Compatibility](https://hexdocs.pm/smolbox/0.3.0/compatibility.html) for the
feature reports and recorded revisions.

Qualification remains `:development`. Exports do not retain RAM, and container
exports exclude `/workspace`. Captures and branches require approved idle,
offline bare guests; no cross-worker migration, portable snapshots, automatic
artifact garbage collection or in-place rollback is implied. Unknown mutations
are not replayed, and observed stop alone cannot fence requests already sent.

These are draft release notes. Final exact-commit CI, tag creation, Hex publication
and documentation availability must be confirmed separately from preparation.
