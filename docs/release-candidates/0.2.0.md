## Release scope and upgrades

0.2.0 combines persistent machines, TCP port mappings, long-running/background
commands, interactive terminals, startup workloads with console diagnostics, and
configurable guest paths/larger files. The default worker is smolvm 1.17.0.
Disposable executions remain supported. Automatic workload restart, application
stdout/stderr capture for startup workloads, OCI/registry provisioning and
streaming bulk file transfer are not added.

The [consolidated upgrade guide](../upgrading-to-0.2.0.md) covers quiescing old
controllers, preserving keys and ownership, PostgreSQL machine/port migrations,
store capabilities and v5–v9 records, retained capacity, worker pinning,
checkpoint compatibility and rollback restrictions. README, installation guides,
ExDoc and package metadata now describe 0.2.0. Historical qualification reports
retain their original revisions and scope.

Library behavior and production dependency constraints match the merged base.
The only library-file edit updates the WorkerConfig module documentation; all
70 library source ASTs match after ignoring documentation and source positions.
The release adds an opt-in integrated acceptance test and a Linux lab harness,
not new runtime features.

## Integrated real-worker acceptance

Both platforms used qualified official smolvm 1.17.0 binaries and the approved
native Python artifacts. They ran the separate 16 MiB file boundary test and
`examples/durable_host/test/release_acceptance_test.exs` in independent `prepare`
and `resume` BEAM processes against PostgreSQL with the same keys and partition.

The integrated test uses **one retained machine** to verify:

1. Immutable startup workload/environment, a fixed host-to-guest TCP mapping,
   explicit `/app` file/cwd policy and codec v9 storage.
2. Staging/readback of a 16 MiB binary, command execution in `/app`, collection
   through the artifact adapter and matching SHA-256.
3. A configured 301-second foreground timeout. The command completes quickly;
   this is budget acceptance, not a new long-duration measurement. Earlier real
   305-second probes remain in their [original report](../long-running-exec-validation.md).
4. Typed background PID, a mapped HTTP response, and terminal input, resizing,
   output and a persisted exit code of 7, followed by console snapshot access.
5. A fresh controller recovering the same machine/configuration, duplicate
   background submission without relaunch, and retained terminal/file contents.
6. Stop/start preserving files and reservations, restarting the startup workload
   exactly once, and keeping the background launch counter unchanged until a new
   explicit execution identity is submitted.
7. Explicit deletion, worker absence, zero disk/slot reservations, and zero
   PostgreSQL port-ownership rows for the partition.

The binary SHA-256 was
`5e033aae0f529e46ba459e41e9b6e91dbff95474e13f258188a04aec0c14b62b`.
Linux used the disposable nested KVM lab through `ssh linux`. Its worker retained
one CPU quota, 1.5 GiB memory, 96 tasks and a five-minute deadline. The successful
campaign took 59.656 seconds, recorded zero OOM kills and a 624,099,328-byte memory
peak. These finite observations are not performance or production isolation claims.

The Linux source archive SHA-256 was
`7c820cbd8a605169921f8ddb4e1da2195abbb221353bb4368d7e517a841989a4`.
All 540 archived files were compared after qualification. Two documented overlays
were present: the lab harness's namespace invocation and the acceptance test's
explicit cleanup phase. Their final hashes are recorded in the JSON evidence;
no application library or package-content overlay was required.

Initial Linux attempts exposed two harness errors: the HTTP probe ran outside the
worker's private network namespace, then GNU `timeout` could not invoke a shell
function used as the namespace wrapper. The final harness runs BEAM as the lab
user inside only the worker's network namespace through an explicit command
array. Isolation controls remain intact. The first attempt's retained machine
was explicitly deleted with verified absence and released reservations before
retrying. All failed and successful capture receipts are retained.

Each completed platform ended with empty owned-machine inventory. macOS stopped
its private worker and PostgreSQL server. Linux stopped the worker, observed no
owned KVM descriptors, exported fsynced phase logs to the physical host and locally,
then stopped the outer lab. Automatic reset was verified against the baseline
checksum, a fresh clean overlay and no active outer process. Exported capture
hashes still matched after reset.

## Reproduce the integrated scenario

Use the durable example's normal PostgreSQL and private worker setup, the approved
2/2 GiB image allocation floor, and a worker read cap of 16 MiB. Choose a free
worker-local port, a fresh store partition and execution ID. Keep the same private
artifact root and keys across both commands. From `examples/durable_host`:

```sh
export SMOLBOX_RELEASE_PORT=19824
export SMOLBOX_EXECUTION_ID=release-020-demo
export SMOLBOX_STORE_PARTITION=release-020-demo
SMOLBOX_RELEASE_PHASE=prepare mix test test/release_acceptance_test.exs --include runtime --warnings-as-errors
SMOLBOX_RELEASE_PHASE=resume mix test test/release_acceptance_test.exs --include runtime --warnings-as-errors
```

Run the controller in the worker's network namespace for the loopback HTTP probe.
The disposable Linux lab wrapper is `scripts/lab/release-020.sh`. The explicit
`SMOLBOX_RELEASE_PHASE=delete` phase cleans up the same known demonstration machine
using its existing keys and identity; do not erase its database partition to retry.
