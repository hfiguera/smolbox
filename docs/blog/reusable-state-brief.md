# Choosing reusable machine state

Mode: Read. The user approved a comparison of exports, checkpoints and branches,
using existing physical Linux measurements, the new workspace demonstration and
SmolBox 0.3.0 as release context. This extends the established article template;
keep its visual identity, navigation, typography and prior articles intact.

Reader question: which state should I reuse for my next workload, and what does
that choice require me to retain? Success is choosing by semantics before speed,
understanding the preparation/cleanup costs, and finding a reproducible example.

OWN-WORLD: inherit the technical field guide: cool paper, navy text, cobalt paths,
amber constraints, flat rules, bounded prose, platform sans and literal code.

STORY: choose what survives; inspect the measured workload; account for preparation
and cleanup; try the saved state example; understand what 0.3.0 adds.

FIRST VIEWPORT: existing article title, short deck, author/version metadata and
an opening problem. The first section contains the interactive state diagram.

FORM: ordinary article extension, no concept roll. A manual four-stage sequence
shows disk/RAM preservation, a distinct saved artifact or live source, then a new
machine and retained cleanup obligations. A static chart uses published median
and p95 data; no animated race or decorative counters. Existing-machine reuse is
an explicit baseline, not a fourth artifact type. Build directly in code.

FINISH: unreviewed and undocumented is unfinished; this build ends with the finish review, the verdict, DESIGN.md, and every shipping raster carrying its provenance

Quality bar: meaningful motion, legible mobile labels, keyboard controls, static
fallback, no autoplay, finite playback that pauses out of view, and reduced motion.
The animation is a teaching model, never a new runtime experiment. Published
measurements retain their warm-cache, one-host, synthetic-workload limitations.
No new qualification campaign or performance ranking is claimed.
